# Intake phase — shop-page upstream questionnaire

This directory holds the **intake mode** assets for `surecart-design-to-shop-page` (collection/listing pages). Intake mode activates when the merchant invokes the skill empty — see Step 0 in the parent `SKILL.md`.

## Sibling-borrow contract (load-bearing)

This skill is intentionally **thin** — it inherits most intake assets from the master sibling `surecart-design-to-blocks/intake/`. Only files that genuinely diverge between product-detail and shop-page surfaces live in this directory:

- `questions.md` — shop-specific questionnaire (catalog type, grid layout, filter UI, card content, pagination)
- `prompt-template.md` — shop-specific 7-section prompt template (3 surfaces: FILTER-CHROME, PRODUCT-GRID, PAGE-CHROME)

**Borrowed from master via lazy reference** (loaded only when intake mode runs):

- `../surecart-design-to-blocks/intake/constraint-digest.md` — single source of truth for the 3-family constraint digest (regenerated by master's `scripts/regen-digest.mjs`; never edit either skill's copy)
- `../surecart-design-to-blocks/intake/shared/anti-patterns.md` — 10 positive-replacement rules (surface-agnostic)
- `../surecart-design-to-blocks/intake/shared/palette-presets.md` — Q2/SQ2 accent → preset slug lookup
- `../surecart-design-to-blocks/intake/shared/tone-presets.md` — brand voice options
- `../surecart-design-to-blocks/intake/shared/typography-presets.md` — Q5/SQ-mood → exemplar handle

This mirrors the established precedent: 9 of 11 `reference/` files in this skill already lazy-reference master's `../surecart-design-to-blocks/reference/*`. The intake-borrow pattern is identical.

## Intake flow (specific to shop-page)

1. Step 0 (in `SKILL.md`) detects empty invocation → routes here
2. `questions.md` runs a small batched questionnaire (max 2 `AskUserQuestion` calls) capturing merchant intent — catalog type, accent, grid layout, filter UI, card content, pagination
3. `prompt-template.md` substitutes answers into a 7-section Claude Design prompt with **shop-specific surface delimiters** (FILTER-CHROME, PRODUCT-GRID, PAGE-CHROME — three surfaces, not two)
4. The constraint digest is referenced from master (no duplicate)
5. The "first card canonical + padding cards isomorphic" rule appears in §7 prohibitions — Claude Design tends to render multiple varied cards by default; the prompt explicitly tells it to vary only photo and title across cards 2–N
6. Merchant pastes the prompt into design.claude.com → returns with the design → Step 0 routes to convert mode

## Validation (Tier I rubric)

The intake-mode validation rubric (Tier I, 9 checks) lives in master's `rubric/self-validate.md` — same 9 items apply here, with one modification at I-2 (surface markers must match the shop-page 3-surface set, not the product-detail 2-surface set).

## Multi-card-collapse converter logic (PR3 additive to Step 3)

The shop-page convert pipeline (Steps 1–5) gains one new behavior in v0.8: when the input design contains N populated product cards inside `<!-- SURFACE: PRODUCT-GRID -->`, Step 3 takes card #1 as canonical, asserts cards 2–N are structurally isomorphic (same children, same wrapper classes — only photo URL and title text vary), and discards cards 2–N before emission. The drift report logs `dropped_features: [{type: "multi_card_collapse", removed_count: N-1, canonical_card: 1}]`.

If cards 2–N diverge structurally (e.g., one has a badge another doesn't, or columns differ), Step 3 bails to a "card structure ambiguity" Tier A warning and asks the merchant to clarify before emitting.

## Zero-regression contract

The intake/ directory is **purely additive**. Convert-mode users see no behavior change from v0.7 (Step 0's convert branch falls through to the existing Steps 1–5; the multi-card-collapse logic only activates for designs emitted with the new surface markers — pre-v0.8 designs flow through Step 3 unchanged).
